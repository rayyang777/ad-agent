# 一、查询工具

通过项目级 `ad_agent` MCP 的 `ad_query` 工具执行 SQL：传入 `sql`，需要时指定 `engine`、`wait`、`fetch_rows` 和 `output_name`。工具会自动提交查询、轮询进度、获取结果，把 CSV 返回给 AI，并保存到项目 `var/ad-agent/`。

- **引擎**：默认 `trino_new`。SQL 必须符合 **Trino 语法**，详见 `knowledge/sql_guidelines.md`。复杂 SQL 可选 `tez_new` / `spark_on_ack`，并确保 SQL 写法符合对应引擎语法。
- **动态分析**：根据前一轮结果决定是否继续查询，不要预设所有下钻 SQL 必须一次完成。

# 二、支持的异动类型与口径

本 skill 覆盖以下 5 类异动；不同异动在**用户级下钻**（基础表）时口径不同，**生成 SQL 前必须先按此表定口径**：

| 异动类型 | 用户级下钻口径 | 字段依据 |
|---|---|---|
| **留存类波动**（次留 / DN 留存率） | **限定新增设备**（`new_equip = '1'`） | 留存指标 `new_udid_day{N}` 仅含新增 |
| **ROI 异常**（N 日 ROI） | **不限新增设备**（含新增 + 回流） | `pay_cny_day{N}` / `cost_cny` 是新增 + 回流口径 |
| **翻倍异常**（M 日-N 日 ROI 翻倍系数） | **不限新增设备**（含新增 + 回流） | 同 ROI |
| **LTV 异常**（N 日 LTV） | **不限新增设备**（含新增 + 回流） | 分母为新增 + 回流总量 |
| **付费率异常**（N 日付费率） | **限定新增设备**（`new_equip = '1'`） | 分子分母都仅含新增 |

> 指标完整定义、汇总表 ↔ 基础表口径映射、用户级下钻具体流程见 `knowledge/metric_definitions.md` 第二、三章。

# 三、分析流程（必须按此顺序执行）

## 前置：维度归属判定

用户提问里的具体值（如「付费智投」、「腾讯广告」、「wechatgame」）通常**不带维度名**。生成任何 SQL 之前，**先判定值属于哪个维度字段**：

1. **查阅** `metric_definitions.md` 3.3「维度值参考字典」—— 直接命中时直接用对应字段（如「智投/手投」→ `account_mode`，「腾讯广告/巨量引擎」→ `media_cn_name`）。
2. **多维度可能命中或字典里没有**，跑 quick discovery SQL 实查（汇总表层面，遵循 `sql_guidelines.md` 第二章约束）：

   ```sql
   -- 例：判定「付费智投」属于 supplier_name 还是 account_mode
   select 'supplier_name' as dim, supplier_name as val, sum(new_udid) as new_users
     from dm_ad.app_et_ad_callback_event_da
    where ds = '<昨天>'
      and supplier_name like '%付费%智投%'
      and report_type = 'ad'
      -- A 类维度全 = 'all'，按 sql_guidelines C3
    group by supplier_name
   union all
   select 'account_mode', account_mode, sum(new_udid)
     from dm_ad.app_et_ad_callback_event_da
    where ds = '<昨天>'
      and account_mode like '%智投%'
      and report_type = 'ad'
      -- A 类维度全 = 'all'
    group by account_mode;
   ```

3. **依然存在多个候选** → 列出 2-3 个候选 + 各自量级供用户确认，**不要擅自选一个继续分析**。

判定完成、维度 + 值都明确后，再进入 Step 1。

## Step 1 — 趋势展示与异常起点判定（汇总表）

从 **汇总表** `dm_ad.app_et_ad_callback_event_da` 提数，按广告维度展示异动指标的整体趋势，**精确定位异常起点**并锁定受影响维度。

- **异常起点判定**：用户描述往往是粗略的（如"4 月开始异常"）。先拉异动指标的日级趋势，**精确判断异常起点的具体日期**，并检查起点**前后一段时间内是否有异常加剧**（先小幅波动后大幅恶化、二次反弹后再下跌等）。最终确定「异常期」用于 Step 2 归因。
- **时间窗口**：异常期和基期**都不超过 1 个月**（半个月 / 1 周更佳）。例：异常期 4-1 ~ 4-15，基期取 3-1 ~ 3-31 即可，不要拉得更长。时间过长会引入历史趋势噪声、数据成熟度衰减，稀释异动信号。
- 不涉及用户 ID，直接按广告维度分组聚合。
- 严守强制约束（`ds = 昨天`、`install_date substr`、A/B 类维度处理、N 日成熟度等），详见 `knowledge/sql_guidelines.md` 第二章。

## Step 2 — 异动归因（基础表用户级下钻）

在 Step 1 锁定的时间窗口和维度上，切到**基础表**做用户级下钻。

**归因重点方向（三选一定位 / 可同时排查）**：

1. **新老用户对比**（`user_type` ∈ `new` / `back`）：异动主要由全新用户还是回流老用户驱动？是判断流量结构变化最直接的切口。
2. **闯关行为**（`stage_times` / `stage_true_times`）：闯关频次与过关率是 Animal 的核心游戏行为指标；留存 / 付费异动经常源自闯关数据异常（关卡难度调整、卡关现象等）。
3. **前端流量变化**（CPI / ecpm / CTR / CVR / CTR\*CVR / 回流占新增比例）：异动是否来自媒体侧投放结构变化？例如 CPI 飙高、CTR 跳水、回流占比异常上升等，往往会直接传导到留存 / ROI / 付费率。
4. 其他维度补充：付费分布、留存衰减曲线、活跃时长等。

**执行规则**：

- **按第二章表格选择口径**（限 / 不限新增设备）。
- 「先定人群，再算指标」：先用 `bi.animal_uid_ray_2026` 圈定用户范围（CTE / 子查询），再 join 付费 / 活跃 / 闯关表。
- **禁止**汇总表与基础表 join。
- 详细规则见 `knowledge/sql_guidelines.md` 第三章、`knowledge/metric_definitions.md` 3.1。

## Step 3 — 报告输出与上传

把 Step 1 + Step 2 结果整理为结构化 `report_data` → 调用 `ad_render_report` 渲染 → 调用 `ad_upload_report` 上传并获取文件 URL。渲染和上传必须是两个独立调用。

# 四、报告内容要求

报告结构：**报告标题 → 元信息模块 → 主体（现状 / 归因）→ 总结模块**，每一层独立成块，都不可省。不得临时生成 HTML、CSS、JavaScript 或报告生成脚本；固定布局与图表逻辑已放在 `assets/report_template.html`，输入结构由 `assets/report_schema.json` 校验。

调用 `ad_render_report` 时固定使用 `template_id="ad-anomaly-v1"`、`local_name="ad-anomaly-report.html"`。`report_data` 顶层结构如下：

`metadata.user` 不由 Skill 填写；`ad_render_report` 会在 Schema 校验前从项目 `config.json` 的 `username` 自动注入，并由模板显示为“产出用户”。配置缺失或为空时直接返回配置错误。

```json
{
  "metadata": {
    "title": "Animal 广告投放 · 付费率异常归因报告",
    "anomaly_type": "付费率异常",
    "metric": "首日付费率",
    "dimensions": ["子平台 = 抖小"],
    "anomaly_period": "2026-07-20~2026-07-31",
    "baseline_period": "2026-07-06~2026-07-19",
    "data_date": "2026-08-01"
  },
  "overview": {
    "scale_metrics": [{"name": "广告新增", "current": "10,000", "baseline": "12,000", "change": "下降 16.67%", "severity": "warning"}],
    "trend_charts": [{"title": "首日付费率趋势", "note": "首日付费人数 / 新增用户数", "dates": ["2026-07-19", "2026-07-20"], "y_axis": "percent", "series": [{"name": "首日付费率", "values": [3.2, 2.8], "kind": "current"}, {"name": "基期均值", "values": [3.3, 3.3], "kind": "baseline"}], "anomaly_start": "2026-07-20", "immature_from": null}]
  },
  "attributions": [
    {"title": "新老用户拆分", "confidence": "confirmed", "conclusion": "...", "details": ["..."], "charts": [], "tables": []},
    {"title": "闯关行为变化", "confidence": "hypothesis", "conclusion": "...", "details": ["..."], "charts": [], "tables": []},
    {"title": "前端流量变化", "confidence": "confirmed", "conclusion": "...", "details": ["..."], "charts": [], "tables": []}
  ],
  "summary": {"confirmed": ["..."], "hypotheses": ["[推测] ..."], "recommendations": ["...", "..."], "monitoring": ["..."]}
}
```

- 图表 `dates` 与每条 `series.values` 必须等长；百分比数值直接传百分数，例如 `2.80` 表示 `2.80%`。
- `kind="baseline"` 由模板显示为灰色虚线，`kind="current"` 使用主题色；不要传颜色或 ECharts 配置。
- 有数据成熟度限制时填写 `immature_from`，否则传 `null`。
- `attributions` 必须严格按新老用户、闯关行为、前端流量三个方向排序；即使未定位原因也要保留该项并写明结论。
- 表格对象使用 `title`、`headers`、`rows`；每行列数必须和表头一致。
- `confidence="hypothesis"` 时，`conclusion` 不写 `[推测]` 前缀，模板会自动添加；`summary.hypotheses` 中的每一项必须自行以 `[推测]` 开头。

**通用规则**：
- **全文中文**：所有文案、字段、维度、指标都用中文。**禁止直接显示英文字段名**（如 `media_cn_name` → 展示为「广告平台」），也**禁止任何英文术语 / 缩写 / 业务黑话**（如 fold、tag、ratio、roi 小写、d2、d7 这种）——LLM 必须把它们映射到 `metric_definitions.md` 里的中文指标名（如「翻倍系数」「关键行为标签」「次日留存率」「7 日 ROI」）。
- **中文命名一致性**：指标 / 维度的中文名严格按 `knowledge/metric_definitions.md` 第二章 / 3.2 / 3.3 字典对应（例：「DN 留存率」「翻倍系数」「广告平台」「关键行为标签」「投放分类」「优化师」「广告账户」「子平台」等）。
- **报告章节直接显示主标题**（如「当前数据现状」），不要写成「第一部分：xxx」这种修饰语。

## 4.0 报告标题与元信息

报告**最顶部按以下两块**展示，**严禁糅在同一深色大卡片里**：

### 报告标题（独立一行）
- 例：`Animal 广告投放 · 翻倍异常归因报告`
- 居中或左对齐均可；可以用主题色背景（参考 4.3 配色），但**不能整片深色**。

### 元信息模块（紧跟标题下方，浅色背景独立卡片块，与正文整体亮色基调一致）
内含 6 项，全部中文：

| 项 | 示例 |
|---|---|
| 异动类型 | 翻倍异常 / ROI 异常 / 留存波动 / LTV 异常 / 付费率异常 |
| 监控指标 | 7 日 ROI、次日留存率、1 日-7 日翻倍系数 |
| 分析维度（关键） | `广告平台 = 巨量引擎`、`关键行为标签 = 每次付费+7日ROI`；多个维度并列 |
| 异常期 | 日期范围（≤ 1 个月） |
| 基期 | 日期范围（≤ 1 个月） |
| 数据日期 | 对应汇总表 `ds = 昨天` |

> 元信息模块**必须遵循 4.3 亮色样式**——浅色背景 + 深色文字 + 浅灰边框，禁止深蓝 / 深紫 / 深黑等大面积深色填充。

## 4.1 当前数据现状

> 不论哪种异动类型，这部分的内容口径固定。

### (a) 广告投放整体盘面

展示**异常期**的核心量级，与基期并列对比：

- **量级**：广告新增 (`new_udid`)、广告整体 (`new_udid + back_udid`)、广告成本 (`cost_cny`)
- **前端指标**：CPI、ecpm、CTR、CVR、CTR\*CVR
- 每项指标给出数值 + 相对基期的偏离 %（涨 / 跌）

### (b) 异动指标自身的波动现状

按异动类型展示**异动指标的时间趋势**：

| 异动类型 | 必展示的趋势 |
|---|---|
| 留存波动 | DN 留存率（涉及的 N 全部展示）随 `install_date` 的变化 |
| ROI 异常 | N 日 ROI 随 `install_date` 的变化 |
| 翻倍异常 | M 日-N 日翻倍系数随 `install_date` 的变化 |
| LTV 异常 | N 日 LTV 随 `install_date` 的变化 |
| 付费率异常 | N 日付费率随 `install_date` 的变化 |

**强制要求**：
- 趋势必须用**折线图**（不要用柱状图 / 表格替代）。
- 异常时间点用**圆点 + 标注 / 异色高亮**突出显示。
- 同图叠加基期参考线（历史均值 / 上周同期）作对比。
- 涉及 N 日指标时遵循 `metric_definitions.md` 1.5 数据成熟度，未成熟段需淡化或标注。

**归因模块同样优先使用折线图**（4.2 节）：
- 凡是**有时间维度的对比数据**（基期 vs 异常期按 install_date 的日粒度变化），一律用折线图，不要只用汇总表格。
- **分组折线图**：同一指标的不同维度（如新用户 vs 回流用户、抖小 vs 微小、不同投放分类）放在同一折线图中叠加，用不同颜色区分，比多个独立表格更直观。
- 表格仅用于**汇总对比**（基期 vs 异常期聚合值），作为折线图的数值补充，不作为主要呈现形式。
- 折线图样式与 4.1(b) 保持一致：基期用灰色 / 虚线，异常期用主题色实线，异常起点用竖线标注。

## 4.2 异动归因

围绕 Step 2 的**三个归因方向**逐一排查，给出明确结论：

1. **新老用户拆分**：异动主要来自 `user_type='new'` 还是 `'back'`？给出各自的指标对比。
2. **闯关行为变化**：`stage_times`、`stage_true_times`（过关率 = `stage_true_times / stage_times`）是否与异动同步变化？
3. **前端流量变化**：CPI / ecpm / CTR / CVR / 回流占比是否在异动时间点同步异常？

> 三个方向逐一排查、给出**该方向是否定位到原因**的明确结论；综合性结论 / 投放建议在 4.4 总结模块统一汇总。

### 结论可信度规范（强制执行）

**每条归因结论必须标明其可信度等级**，不得将推断当事实陈述：

| 等级 | 标识 | 使用条件 | HTML 样式建议 |
|------|------|---------|--------------|
| **已证实** | 无额外标注 | 数据直接计算得出，无需额外假设 | 正常蓝色结论框 |
| **推测** | 在结论文字前加 `[推测]` 标签 | 逻辑合理但数据只能证明相关，无法证明因果；或需要额外信息才能确认 | 橙色 / 黄色结论框，并注明「建议向运营侧确认」 |

**常见的"推断误区"——以下类型结论一律标为 `[推测]`**：
- 将时序相关表述为因果：「A 指标变化**导致** B 指标变化」——除非有机制链路数据支撑，否则只能写「A 与 B 存在时序关联」
- 推断媒体 / 平台的算法行为：「eCPM 飙升触发算法重新寻量」「算法漂移至 xxx 人群」——算法黑盒，数据不可见，必须标 `[推测]`
- 推断运营侧操作：「是因为有人调整了定向」——除非有直接日志证据
- 推断竞争环境：「竞品加量导致 eCPM 上升」——数据不可见

**数据只能直接支撑的结论类型**（可以不加标注）：
- 指标在时间上的变化量（「7 日翻倍系数从 X 降至 Y」）
- 用户行为在基期 vs 异常期的差异（「首日人均付费上升 X%，7 日付费人数下降 Y%」）
- 投放结构变化（「XX 投放分类在 X 日后新增出现」）
- 两个指标的同步 / 不同步（「eCPM 升高与翻倍系数下滑存在时序关联」）

## 4.3 HTML 样式要求

- **整体基调（强约束）**：**亮色系**——背景浅色（如 `#ffffff` / `#f7f9fc` / `#fafbfc`），文字深色（如 `#1f2937` / `#111827`）。**所有模块**（含 4.0 元信息、4.1 / 4.2 主体、4.4 总结）都必须遵守，**禁止局部使用深蓝 / 深紫 / 深黑大面积填充**——总结模块尤其要避免"反差色块"风格，与正文一致才算合格。
- **配色搭配**：避免高饱和度撞色。建议主色（蓝 / 青系）+ 强调色（橙 / 红，仅用于异常突出）+ 中性灰阶。主题色仅用于**线条 / 图标 / 强调字 / 边框**，不要用作整块背景。
- **数据强调**：异动数值用主题色或红色高亮文字，常规数值用灰阶字号区分。
- **折线图**：基期参考线用淡灰色，当前期用主题色实线，异常点用圆点 + 醒目标签。
- **卡片 / 分块**：使用浅灰边框或柔和阴影分块，每块独立、间距清晰；不要把多块挤在一个大深色容器里。

## 4.4 总结模块（报告底部）

报告必须以**总结模块**收尾，TL;DR 风格、文字简洁，包含：

1. **归因分析结论**：概括异动主驱动因素，**严格区分已证实事实与推测**：
   - 已证实部分：直接写结论（数据直接支撑）
   - 推测部分：用「[推测]」前缀标注，并附上建议向谁确认
   - 禁止将相关关系表述为因果关系
2. **投放建议**：列出 **2-4 条** 具体可执行动作。
   - 定位明确 → 给操作建议（调整某媒体出价、暂停某关键行为标签、关注某优化师账户、关卡难度调整、调整投放分类等）。
   - 未定位明确 → 给下一步探索线索（更细维度下钻、对比竞品 / 版本时间点、确认数据管线等）。
3. **后续监控**：建议持续观察的指标 + 维度组合，便于复盘。

# 五、上传报告

先调用 `ad_render_report`，传入 `template_id=ad-anomaly-v1`、完整 `report_data`、`local_name=ad-anomaly-report.html`。Schema 校验失败时只修正错误指出的数据字段，不得改写模板、生成临时脚本或改用完整 HTML 上传。

渲染成功后调用 `ad_upload_report`，传入返回的 `report_file`、`title=<metadata.title>`、`today=<报告产出日期>`，不要传 `upload_name`。工具自动使用 `<报告标题> - <日期>.html` 作为飞书文件名并返回本地报告路径和飞书 URL；标题中的 `/` 自动替换为 `、`。
