# Animal 指标查询

根据项目知识库确定业务口径、数据表和 SQL，通过本地 MCP 执行只读查询，向用户返回可核验的结果。默认不生成或上传 HTML 报告。

## 查询流程

1. 读取项目根目录下的共享知识库：
   - `knowledge/project.md`：产品端、`appid`、归因口径和用户/设备属性；
   - `knowledge/metrics.md`：指标定义、公式、适用人群和成熟规则；
   - `knowledge/tables.md`：表能力、字段、粒度、分区和目标表维度映射；
   - `knowledge/sql.md`：表路由、过滤、聚合、关联和 SQL 约束；
   - 需要解释简称或维度值时，再读取 `knowledge/dimensions.md`。
2. 从用户问题识别指标及周期、产品端或 `appid`、日期范围、时间粒度、展现类型、业务维度和输出形式。
   - 用户只指定指标类别而未指定周期时，按 `knowledge/metrics.md` 中的常用周期展开，不得只返回“截至当前”。例如只说“看下 LTV”时，默认查询并输出 `1日LTV`、`3日LTV`、`7日LTV` 和 `截至当前LTV`；若某周期不成熟，按成熟度规则处理。
3. 严格按 `knowledge/sql.md` 的流程选表、生成 SQL 和执行查询；不得根据印象猜字段、维度值或公式。
4. 查询完成后按“结果校验”检查口径，再按“结果输出”组织回答。

## 必须遵守的边界

- `knowledge/sql.md` 是 SQL 规则的唯一详细来源。遇到表路由、分区、跨表合并、成熟度或明细关联问题，按该文件执行，不在本 skill 中另行推导。
- 先从 `dimensions.md` 识别标准业务维度，再从已选目标表在 `tables.md` 中的映射确定物理字段；不能根据字段名猜测，也不能把一张表的映射套用到另一张表。
- 用户未指定产品端时，按 `project.md` 的默认规则处理；如果缺少会实质改变口径的信息，先询问，不在信息不完整时查询。
- 只生成单条只读 SQL。默认调用 MCP 工具 `ad_query`，使用 `trino_new`；预计耗时较长时使用 `ad_query_submit`、`ad_query_status` 和 `ad_query_result`。
- 只有 SQL 复杂度确实需要或执行日志明确显示引擎能力问题时，才切换到 `tez_new` 或 `spark_on_ack`；语法、字段、权限或业务条件错误不能通过盲目切换引擎解决。
- 用户级净收入必须遵守 `knowledge/sql.md` 的 `LEFT JOIN` 分成比例规则，使用 `COALESCE(rate, 1)`，不能因分成比例未匹配而丢弃付费记录。
- 用户级明细查询必须按归因周期处理：用户归因表按 `ds + udid` 去重，不能在整个时间范围内只按 `udid` 去重；活跃、付费等行为日期必须满足 `>= install_date` 且 `< stop_date`。

## 结果校验

返回前检查：

- 产品端、日期、展现类型、业务维度和用户/设备口径与问题一致；
- 指标公式、单位、小数位和百分比展示正确；
- N 日指标只包含成熟日期，未成熟值不填 0；
- 多表结果的日期、维度和粒度一致，没有因 `JOIN`、`UNION` 或多层聚合造成重复或数据丢失；
- 汇总表无数据时，先检查分区和过滤条件，再按 `sql.md` 的路由顺序尝试其他汇总表或用户级明细表，不能直接返回空值；
- 返回行数达到查询上限或结果被截断时，缩小明细范围或在 SQL 内聚合，不能把不完整结果当成全量结果。
- 指标名称必须逐一对应 `knowledge/metrics.md` 的基础指标名称。可以根据上下文增加产品端、日期、展现类型或统计范围等前缀/后缀，但不能自行创造、缩写、合并或替换指标名称；尤其要严格区分用户指标和设备指标。
- 汇总值必须基于完整查询范围和完整结果计算，不能根据展示出来的部分明细反推汇总值。

## 结果输出

默认同时输出两部分：

1. **汇总数据**：先展示用户所选完整日期范围、产品端、展现类型和维度下的汇总指标；汇总表放在回答最前面。
2. **分天或分维度明细**：再展示按用户要求的日期、维度或端口拆分结果。明细行较少时完整展示；天数或行数较多时只展示具有代表性的几行，并注明“明细共 X 行，当前展示 Y 行”，不能让截取后的明细看起来像完整结果。

如果用户明确只要汇总或只要明细，按用户要求输出；否则不能只输出其中一部分。简单查询保持简洁，只有用户要求分析原因时才扩展分析。
