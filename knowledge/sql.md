# Animal SQL 查询规范

## 分区条件（强制）

- 所有有分区的事实表查询都必须限制完整分区键`ds`和`appid`。`ds`条件按`tables.md`中的`ds读取类型`执行：`全量快照`固定使用`ds=昨天`，`日增量明细`按事件日期范围限制`ds`；无分区表不添加`ds`条件。
- `ds`的业务含义由`tables.md`中的`ds读取类型`决定：全量快照表中是快照日期，日增量明细表中是事件日期，用户归因表中是用户新增日期。用户新增日期字段仍需按表结构使用`substr(install_date, 1, 10)`等方式筛选。
- 内购分成比例表 `dm_ad.dim_et_custom_pay_da` 无分区键，不添加`ds`条件；如存在`appid`字段，按目标产品过滤。
- 未指定产品时不能省略 `appid` 条件；应先根据用户问题确定产品，无法确定时先询问。

## 表路由流程

生成 SQL 前按以下顺序执行：

1. 识别指标、维度、过滤值、日期范围和时间粒度。
2. 在 `dimensions.md` 将用户说法转换为标准业务维度名称；`版位`统一识别为标准维度`子平台`，但不要在此步骤确定物理字段。
3. 在 `metrics.md` 确认指标公式和默认来源。
4. 在 `tables.md` 确认候选表是否同时支持该指标和全部指定维度，并只使用目标表自己的“业务维度与物理字段”映射。
5. 先按产品端确定默认表路由：
   - APP端（`animal_androidcncm_prod`、`animal_ioscn_prod`、`animal_ohoscn_prod`）未指定关键行为时，必须优先使用能够提供目标指标和全部维度的APP每日汇总表；不能因为关键行为表能一次返回多个指标就改用关键行为表。
   - H5端（`animal_h5cn_prod`）无论是否指定关键行为维度，优先使用关键行为汇总表 `dm_ad.app_et_ad_callback_event_da`；该表不支持目标指标或指定维度时，使用支持该口径的用户级明细表。
6. 无论产品端如何，用户指定 `行为标签`、关键行为专属的 `投放分类`，或指定 `投放类型 = 关键行为` 时，使用 `dm_ad.app_et_ad_callback_event_da`或使用明细表查询，并保留对应关键行为过滤条件。
7. APP端只有明确指定上述关键行为条件时才使用关键行为汇总表；其他APP查询优先使用每日汇总表，指定维度不受每日汇总表支持时使用支持该口径的用户级明细表。H5端按第5条优先使用关键行为汇总表，指标或维度不受支持时使用用户级明细表。
8. 需要用户分群、用户级付费、活跃或闯关时，使用用户归因表先圈定人群，再关联对应明细表。由于游戏通服，归因端`appid`与行为端`appid`不是同一个概念：归因表按目标买入端过滤，付费、活跃和闯关明细默认使用四端`appid`范围；只有用户明确指定行为端时，才限制为单个行为端。
9. 如果一张表不能同时满足指标、维度和口径要求，不要用不完整结果替代；应说明缺失的字段或能力。
10. 每日汇总表或关键行为汇总表查询目标指标时，如果结果为空、指标字段无记录或目标分区没有该指标数据，不能直接向用户返回空值。先检查`ds`、`appid`、展现类型、维度过滤和N日成熟条件；确认不是查询条件问题后，必须改用支持同一口径的用户级明细表查询。只有明细表也没有符合条件的数据时，才能说明该指标暂无数据。

## 按维度选择数据表

先根据用户指定的维度判断候选表范围：

| 用户指定的维度 | 表选择规则 |
|---|---|
| `行为标签`、关键行为专属的 `投放分类` | 只能使用关键行为汇总表。其他表即使存在同名字段，也不能直接替代，除非表目录明确说明它们具有完全一致的关键行为口径。 |
| `投放类型 = 关键行为` | 只能使用关键行为汇总表，并在查询条件中保留关键行为类型过滤。 |
| 仅指定通用维度，例如展现类型、广告平台、来源平台、投放账户、日期 | APP端优先使用APP每日汇总表，指定维度不支持时使用用户级明细表；H5端优先使用关键行为汇总表，指标或维度不支持时使用用户级明细表。 |

“可以同时在关键行为汇总表和其他表查询”表示通用维度场景下允许选择不同候选表或做结果对照，不表示可以把两张已经聚合的数据直接相加。跨表合并前必须确认粒度、去重规则、时间口径和指标定义一致；否则分别查询并说明差异。

## 默认引擎

- 默认引擎：`trino_new`
- 复杂查询可使用 `tez_new` 或 `spark_on_ack`
- 引擎变化时，SQL 语法必须同步适配

## APP每日汇总表规则

APP每日汇总表的具体指标字段见 `tables.md`。

### 指标路由

| 查询指标 | 优先数据表 |
|---|---|
| 广告成本、曝光、点击、预约 | `dm_ad.app_et_ad_cost_report_da` |
| 新增设备、实名新增设备、固定成本 | `dm_ad.app_et_ad_equip_new_da` |
| 回流设备 | `dm_ad.app_et_ad_equip_back_da` |
| 首日在线时长、登录和等级行为 | `dm_ad.app_et_ad_firstday_da` |
| N日留存 | `dm_ad.app_et_ad_retention_da` |
| N日付费设备数、截至当前付费设备数 | `dm_ad.app_et_ad_pay_num_da` |
| 新增或回流N日累计收入 | `dm_ad.app_et_ad_revenue_da`、`dm_ad.app_et_ad_back_revenue_da` |

### 查询条件

- APP每日汇总表按新增日期统计，日期筛选、分组和排序统一使用 `substr(install_date, 1, 10)`。
- APP每日汇总表和关键行为汇总表的`ds读取类型`为`全量快照`，固定使用`ds=昨天`并同时限制`appid`，不使用`ds`日期范围。新增日期范围统一通过`substr(install_date, 1, 10)`筛选。
- APP端口使用 `animal_androidcncm_prod`、`animal_ioscn_prod`、`animal_ohoscn_prod`；只查询用户指定的端口，未指定APP端口时才使用全部APP端口。
- `report_type` 使用真实值。用户说“广告量”时默认使用 `report_type = 'ad'`；用户说“测试量”或“广告测试”时使用 `report_type = 'adtest'`。`deeplink`、`deeplink-测试`、`deeplink-直拉`、`mkt` 等其他值不自动并入“广告量”，只有用户明确指定或业务规则明确说明时才使用；`organic`表示自然量。正式查询前仍需确认目标表昨天分区实际存在目标值，若不支持则说明无法查询。
- `media_cn_name` 使用真实值或按该维度分组，不使用 `= 'all'`。
- 已选定每日汇总表后，先读取`tables.md`中该表自己的业务维度与物理字段映射，再生成SQL。不能将其他表的字段映射套用到每日汇总表。用户说`版位`时，先按`dimensions.md`识别为标准维度`子平台`，再查该目标表中`子平台`对应的字段。这些投放细分维度不分析时必须使用`= 'all'`；分析某个维度时使用真实值并加入`GROUP BY`。
- 月度累计字段使用 `max` 聚合，日级可加总字段使用 `sum` 聚合。不要对月度累计字段再次求和。
- `back_equip_total` 在模板中使用 `try_cast(... as bigint)` 后再求和。
- `{N}`是字段模式，不是可直接执行的字段名。生成SQL时必须替换为实际周期，例如 `new_udid_day7`；使用前在目标表中确认该周期字段存在。
- 查询新增和回流整体收入时，分别从新增表和对应回流表取数，再按完全一致的维度与日期粒度合并。不得只取新增表后称为整体收入。
- 汇总表指标无数据时，不能把空结果当作指标为0或直接返回“无数据”。应按表路由规则回退到用户级明细表核验底层数据；明细表也无数据时，才返回暂无数据及可能原因。

## 关键行为汇总表规则

表：`dm_ad.app_et_ad_callback_event_da`

- `ds`读取类型为`全量快照`，必须等于昨天；`appid`是产品分区，必须同时限制目标产品，不使用日期范围。
- `install_date` 是带时间的字符串，所有日期筛选、分组和排序都使用 `substr(install_date, 1, 10)`。
- 用户明确指定正式广告量或直接说广告量时使用 `report_type = 'ad'`；用户说测试量或广告测试时使用 `report_type = 'adtest'`。其他投放来源值只有在用户明确指定时才使用。
- `广告平台`对应`media_cn_name`，`展现类型`对应`report_type`，二者按真实值处理，不过滤为`'all'`。
- 关键行为表的字段映射以本节字段表为准。只有确认目标表中的业务维度与物理字段对应关系后，才能生成过滤条件；不能将每日汇总表或其他表的同名字段映射套用到关键行为表。这些投放细分维度不分析时必须使用`= 'all'`；分析某个维度时使用真实值并加入`GROUP BY`。多维聚合时，所有未加入`GROUP BY`的投放细分维度都必须保留`= 'all'`，不能省略条件。
- `pay_cny_day{N}` 已经是净收入，不再关联内购分成比例表。
- 汇总表不与用户归因表、付费明细表、活跃明细表或闯关明细表直接关联。

## 用户级明细规则

- 用户归因表、付费明细表、活跃明细表和闯关明细表都必须同时限制 `ds` 与 `appid`。用户归因表的`ds`按用户新增日期范围限制；付费、活跃和闯关明细的`ds`按目标事件日期范围限制，不固定为昨天。通服分析时，归因表的`appid`限制买入端，明细表的`appid`默认限制四端范围，不能只使用归因端`appid`。
- 先在 `bi.animal_uid_ray_2026` 圈定用户，再关联明细表。
- 用户 ID 默认对应关系：用户归因表 `udid` = 付费表 `user_id` = 活跃表 `uid` = 闯关表 `uid`。付费表中的 `udid` 是设备标识，不作为默认用户关联键。
- 付费设备数和付费率必须按去重后的 `user_id` 统计，不能按订单行数统计。
- 活跃日级统计优先使用活跃表 `ds`；付费事件日期使用 `paytime` 截取日期。留存日通过新增日期与活跃表 `ds` 的日期差计算。
- 用户级净收入必须将付费明细的 `pay_amount_cny` 与 `dm_ad.dim_et_custom_pay_da.rate` 相乘，并按 `appid`、`pay_type`、`platform` 和付费时间对应的生效区间匹配内购分成比例记录。
- 只分析新增设备时，用户归因表使用 `report_type = 'ad' and new_equip = '1'`。
- 分析新增和回流整体时，不限制 `new_equip`。
- 人群筛选优先按用户说法判断层级：用户明确说`新用户`、`老用户`或`回流用户`时，只限制`user_type`，不限制`new_equip`；用户未提及用户层级，只说`新增`、`新增设备`或`回流设备`时，只按设备属性限制`new_equip`，不限制`user_type`。两类条件不能互相替代。
- 用户级明细存在一对多关系时，先在用户或订单粒度去重，再进行设备数、付费人数和收入汇总。

## SQL 安全与结果控制

- 只生成单条只读查询，不生成写入、删除或修改语句。
- 比率计算使用 `nullif` 防止除零，并显式进行浮点计算。
- 输出字段使用清晰的中文别名或稳定的业务字段名，便于后续分析。
- 查询条件必须覆盖产品、日期和必要的广告来源条件。
